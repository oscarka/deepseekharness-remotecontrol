# 飞书控制方案与安全加固

> 针对你的两个要求：**不走作者服务器**、**控制放在飞书里**。  
> 结论先说：方向可行，但不能靠改 `ds-harness-remote` 的配置实现——它的 server 是控制面，不是可替换的“中转地址”。要走飞书，需要做一个**本地飞书桥插件**，让飞书只做“消息 + 身份”，DSH 仍然在本机执行和审批。

---

## 一、为什么不能把 ds-harness-remote 直接改成飞书

`ds-harness-remote` 的 Server 承担的不只是“转发”：

- 账号注册/登录、设备注册与撤销
- Host/Client 在线状态与 presence
- 连接协调、WebRTC signaling、TURN 凭据
- Relay 兜底、限流、协议版本协商
- 设备 membership 校验

客户端和 Host 的协议、身份、重连状态机都围绕这套 Server 设计。  
**把 Server URL 换成飞书，不会工作**；把 Server 换成你自己，仍然需要一个常驻公网服务。  
所以你的方向应该是：**去掉 relay，飞书直接作为控制面**。

---

## 二、推荐架构：本地飞书桥 + 飞书长连接

如果同时保留 Web 和飞书，最干净的做法不是“Desktop + relay + 飞书”，而是：

```text
                    ┌──────────────────────────────┐
浏览器（Tailscale）  │   dsh web 单一 Host 进程       │
        ───────────▶│   ├─ 官方 Web UI / sessions    │
                    │   ├─ dsh-feishu 插件            │
飞书自建应用         │   └─ ctx.agents / approval      │
        ───────────▶│                                │
   （长连接，只出站） └──────────────────────────────┘
```

关键点：

- **一个 Host，两个入口**：Web 和飞书看到的是同一批 live sessions，不是两套会话。
- **没有公网端口、没有公网 IP、没有 Relay、没有作者服务器。**
- 飞书负责“谁能发消息、消息送到哪”；DSH 负责“能不能执行、要不要审批”。
- Web 用官方 token + Cookie + Host/Origin 栅栏；飞书用自建应用 + open_id 白名单。
- 代价：插件与 DSH 版本耦合。DSH 升级（尤其 rc 之间）要回归测试。

### 2.1 为什么选 `dsh web` 作为唯一 Host

- 官方 `dsh web` 就是完整的浏览器界面（聊天、模型、设置、历史），不需要 Remote Web 或 relay。
- 飞书插件装在 `web` profile 里，和 Web UI 同进程，所以能拿到同一批 `ctx.agents` 和审批。
- Desktop 的 `56430` 只监听 loopback、要 Electron 内部 token，外部 Web 很难干净地接进来；把 Desktop 当 Host 会让“Web + 飞书”变成两套入口。
- 因此：**日常任务在 `dsh web` 里跑，Desktop 只作为本地窗口或备用。** 如果任务在 Desktop 里跑，飞书/Web 的 `dsh web` Host 看不到它的实时 Agent。

启动方式（Tailscale 直连，最省事）：

```bash
# 1. 启动 Tailscale，拿本机 tailnet IP
tailscale up
tailscale ip -4          # 例如 100.101.102.103

# 2. 只绑这个地址，不绑 0.0.0.0
dsh --profile web --host 100.101.102.103 --port 3080 --no-open

# 3. 手机/笔记本（同一 tailnet）打开启动时打印的：
#    http://100.101.102.103:3080/?token=...
```

Tailscale 本身是 WireGuard 加密，tailnet 内用 HTTP 可以接受；如果要 HTTPS 域名，再在前面挂 Caddy 或 Tailscale Serve，并给 `dsh web` 配 `--public-url` + `--trusted-host`。

**不要**为了 Web 再去跑 `apps/server` 的 Docker relay：  
`apps/server` 的 Web 只是设备状态页，完整 Remote Web 在另一个仓库；而且它 relay-only、单账号、无 2FA，属于“为了一个 Web 入口多养一个公网服务”，不划算。

### 2.2 为什么不用“自建 relay + 飞书通知”

那仍然是“一个常驻服务器 + 一套账号/设备协议”，只是服务器换成你的。  
你要的是“Web + 飞书”，`dsh web` 已经同时满足；relay 只在你要保留 DSH Remote 的 Android/Web 原生客户端时才需要，而且应该放到 VPS/Tailscale，不是本地 Docker/Cloud Run。

## 三、最小可用命令面（MVP）

建议第一期只做这些，不做终端、不做任意文件读写：

| 飞书里发 | 行为 |
| --- | --- |
| 直接发文字 | 发给当前绑定的 DSH 会话（`agent.followup`） |
| `/status` | 当前会话状态、最近一条 assistant 输出（截断） |
| `/sessions` | 列出本机 live 会话 |
| `/use <sessionId>` | 把当前飞书聊天绑定到某个会话 |
| `/stop` | 中断当前执行（`agent.cancel`），不删除队列 |
| `/approve <code>` | 批准一条待审批工具调用 |
| `/deny <code>` | 拒绝一条待审批工具调用 |
| `/help` | 命令说明 |

明确不做：

- `/exec`、任意 shell
- 远程终端
- 任意路径文件上传/下载
- 自动批准
- 群聊里无 @ 的广播控制

第二期再加：`/new <cwd>`、流式分段输出、审批卡片按钮、图片输入、任务完成通知。

## 四、安全模型（P0，必须做）

### 4.1 身份与准入

1. **只认 `open_id` 白名单**，不认昵称、邮箱、`user_id` 之外的展示字段。
2. **默认只允许单聊（p2p）**；群聊只做通知，或必须 @机器人 + 单独白名单。
3. 未授权用户：不回显任何会话信息，只回“无权限”，并记审计日志。
4. 校验事件 `header.app_id` / `tenant_key` 与配置一致；按 `event_id` 去重；忽略机器人自己发的消息，防止回环。

### 4.2 凭据

- 飞书 `App Secret` 放 macOS Keychain 或 DSH credential store，**不要**放仓库、明文 YAML、日志。
- 文件权限 0600；启动时校验；支持轮换。
- 只申请最小权限：接收单聊消息、以机器人身份发消息；不要通讯录、云文档、日历等无关权限。

### 4.3 Web 入口

- `dsh web` 只绑 **Tailscale IP 或 127.0.0.1**，永远不绑 `0.0.0.0`，不把 3080/56430 映射到公网。
- 启动打印的 `?token=...` 只进密码管理器，不进群、不进截图、不进 shell history；Cookie 默认 30 天，重启进程会换新 token。
- 用 Tailscale ACL 限制只有你的设备能访问该端口；不要用 Funnel 把它开到公网。
- 若前面挂 Caddy/Nginx/Tailscale Serve：必须 HTTPS，`--trusted-host` 只写精确域名（不要通配），`--public-url` 与浏览器地址完全一致。
- Web token 泄漏 = 完整控制权，和飞书 App Secret 同级；两者都要能独立轮换。

### 4.4 审批

- 每条审批生成 **8 位一次性 code**，TTL 120 秒。
- code 绑定：`chat_id + session_id + toolName + callId`；换聊天、换会话、换工具都无效。
- 只允许发起该任务的用户，或配置里的固定审批人；其他人回复一律拒绝。
- 超时 = `rejected`/`unavailable`，**绝不自动允许**。
- 同一会话同时只允许一个待审批，避免“批错任务”。
- 审批消息只发工具名、原因、风险级别；不回显完整参数（参数可能含密钥）。

### 4.5 执行边界

- DSH approval policy 保持 `ask`，不改成 `never` 或自动允许。
- 沙箱保持 `workspace-write`；不要为了远程方便改成全盘写。
- 远程终端关闭；`remote_*` 工具关闭；ACP 后端按需关闭。
- 插件只调用 `agent.followup` / `cancel` / `approval`，不直接调 `bash`。

### 4.6 输出与留存

- 回复截断（例如 4k 字符），长内容分页/摘要，不整段回传。
- 对 `sk-`、`Bearer`、`PRIVATE KEY`、常见 token 格式做脱敏。
- 默认不回传文件内容；要看文件，走官方 Web/Tailscale，不在飞书里传。
- 审计日志：`~/.dsh/feishu-audit.jsonl`，0600，记录 event_id、open_id、chat_id、session_id、动作、审批结果、时间；定期轮转。
- **飞书不是 E2E**：企业租户管理员/合规系统理论上能读取消息。不要把生产密钥、客户数据、完整源码贴进飞书。这一点无法用插件消除。

### 4.7 可用性防护

- 每用户 10 条/分钟、每聊天同时 1 个执行；超出排队或拒绝。
- 输入上限 8k 字符；超长拒绝并提示分段。
- 飞书 WS 断线重连；事件按 `event_id` 幂等；重连后主动拉一次会话状态，避免“断线期间的消息丢了却不知道”。
- Mac 休眠 = 机器人离线；需要 `caffeinate` 或常开机器。

## 五、如果你还保留 ds-harness-remote，先打这些补丁

即使最终走飞书，下面这些也适用于任何“远程能操作 DSH”的部署：

| 优先级 | 项 | 做法 |
| --- | --- | --- |
| P0 | 远程终端 | Host 设置里关闭 `terminal.enabled`；不要给远程 shell |
| P0 | 远程工具 | 关闭 `remoteTools.enabled`，避免本机 Agent 反向驱动远端 |
| P0 | ACP 后端 | 只保留实际用的；Codex/Cursor/Claude/Pi 不用就关 |
| P0 | Server | 不再用作者服务器；如自建，只绑 Tailscale 地址 + TLS + 强密码，不暴露公网 |
| P0 | 设备 | 撤销不用的设备；新设备登录要复核 |
| P1 | 版本 | 钉 0.5.23；升级前看 #185/#140 与 compatibility |
| P1 | 账号 | 唯一强密码 + OAuth 2FA；不与其它服务复用 |
| P1 | 日志 | 不开 debug 到公网；日志里不出现 token/密码 |
| P2 | 供应链 | `pnpm audit --prod`；APK 校验哈希；不自动更新 |
| P2 | 备份 | 自建 Server 的 `state.json` 备份与权限（含 scrypt verifier/设备记录） |

### 自建 Server 的额外检查

仓库里的 `apps/server` 已经做得不错：

- 密码用 `scrypt` verifier，不存明文
- token 只存 SHA-256 摘要
- 登录/接口有速率限制
- Cookie `HttpOnly; SameSite=Strict`，HTTPS 下 `Secure`

仍需注意：

- `DSH_SERVER_PASSWORD` 放环境变量/密钥管理，不要写进 compose 文件提交
- 必须放在 HTTPS 反代后，且 WebSocket `/ws/v1/connect` 要支持 Upgrade
- 绑定 `127.0.0.1` 或 Tailscale IP，不要 `0.0.0.0` 裸奔
- 单账号模型没有多用户隔离；不要把账号借给别人
- `state.json` 含设备公钥与 token 摘要，按凭据级别保护

## 六、还有哪些没解决的问题

1. **DSH 没有公开的“外部附着到 live session”API**。  
   想接管当前 Host 正在跑的会话，只能做进程内插件；这会随 DSH 版本变化。rc.3 → 后续版本要持续回归。
2. **飞书不是 E2E**。  
   这是架构决定的，不是补丁能解决的。敏感内容要么不发飞书，要么只发“任务已完成/需要审批”这种元信息。
3. **飞书消息长度/频率限制**。  
   长输出必须分段、摘要、限流；审批卡片回调也比纯文本复杂。
4. **多用户/多会话并发**。  
   MVP 建议“一个飞书聊天绑定一个会话、同时一个执行”，先不做多人协作。
5. **Mac 休眠/断网**。  
   飞书事件可能丢失或延迟；需要幂等 + 重连后状态同步，不能假设“发出去就一定执行”。
6. **插件权限与 DSH 升级**。  
   插件拿到 `ctx.agents` / `ctx.approval` 是很高的权限；代码要最小化、可审计，安装前要 review。
7. **合规**。  
   公司飞书租户可能禁止自建应用/长连接/机器人外发；需要管理员确认。

## 七、实施计划

### Phase 0：确认（今天）

- 飞书自建应用是否已创建、是否有管理员权限
- 只允许你自己（open_id 白名单）还是另有审批人
- 只做单聊，还是群聊也要
- 是否接受“飞书租户可见消息内容”这个前提

### Phase 1：MVP（约 1–2 天）

- `dsh-feishu` 插件骨架：配置、WS 长连接、白名单、审计
- 文本 prompt、`/status`、`/sessions`、`/use`、`/stop`
- 审批：`approval/request` → 飞书消息 + code → `/approve` `/deny`

### Phase 2：可用性

- `/new`、流式分段、审批卡片、完成通知、断线重连、限流

### Phase 3：加固

- 脱敏、审计轮转、密钥轮换、渗透测试清单、升级回归

## 八、飞书应用配置清单（给管理员/你自己）

以飞书开放平台实际文案为准，大致需要：

1. 创建**企业自建应用**，启用**机器人**能力。
2. 权限（最小集）：
   - 接收单聊消息（`im:message.p2p_msg:readonly` 或对应文案）
   - 以机器人身份发送消息（`im:message:send_as_bot`）
   - 如要群聊 @：群聊 @ 消息读取权限
3. 事件订阅：
   - `im.message.receive_v1`（接收消息）
   - 订阅方式选**长连接**（不需要公网回调地址）
4. 发布版本，等管理员审核通过。
5. 把机器人加到你自己的单聊/目标群。
6. 把 `App ID` / `App Secret` 放到本机安全配置，**不要发在聊天里**。

## 九、一句话总结

**不要改造 ds-harness-remote 去接飞书；做一个本地 `dsh-feishu` 插件，飞书只做消息与身份，DSH 保留执行与审批。**  
这样没有作者服务器、没有 relay、没有公网端口；代价是失去 E2E、插件与 DSH 版本耦合，并且必须把审批、白名单、脱敏、审计做扎实。

## 十、MVP 验证结果（2026-10-29）

测试企业自建应用（`cli_xxxxxxxxxxxxxxxx`）已验证：

- 租户 token、机器人信息、飞书 WS endpoint 握手成功
- `dsh web` 临时 profile 加载 `dsh-feishu`，审计出现 `transport: ready`
- 飞书 → 桥 → DSH：`/whoami`、`!ping` 收到并回复
- 桥 → 飞书：主动私聊、群消息发送成功
- 用测试探针在真实 DSH `ctx.agents` 上验证：`!sessions`、`!use <id>`、prompt 发送、assistant 回复捕获均正常
- 真实模型 key 仍返回 401，prompt 验证使用本地 mock OpenAI-compatible 服务完成；生产前必须换有效 key

发现并修复：

1. 飞书客户端会拦截未注册的 `/sessions`、`/use` 等 slash 命令，平台返回 "Unknown command"，桥收不到。命令前缀改为 `!`（`!sessions`、`!use`、`!status`…），`/...` 仍兼容能送达的客户端。
2. 一个 agent 只能绑定一个控制 chat；重新 `/use` 会清掉旧 chat 的审批权。
3. `allowedOpenIds`、`allowGroup` 可从 0600 的 `~/.dsh/feishu.env` 读取，不需要手改 profile。
4. 增加 `tenantKey` 可选校验、`FEISHU_DEBUG_EVENTS` 诊断、`!ping`。

- 把 `~/.dsh/feishu.env` 放到真实 `~/.dsh`，安装到真实 `web` profile
- 用有效模型 key 跑一次真实 prompt
- 触发真实审批工具，验证 `!approve` / `!deny` 的端到端
